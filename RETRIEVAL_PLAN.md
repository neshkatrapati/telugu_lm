# Stage B Plan — Tool-Use SFT with Multi-Pack Retrieval

Concrete plan for building the SFT dataset and training the model to do retrieval-augmented synthesis across multiple "packs". Supersedes the Stage B section in `RETRIEVAL.md`.

## Product vision

The trained model lives inside a **mobile app**. The app has multiple **"packs"** — addressable retrieval sources, each with different content:

- **Offline packs** (downloaded to device): Telugu Poetry, Textbooks, Books, etc.
- **Online packs** (fetched via network): Wikipedia, internet web search

For a given user question, the model must:
1. Read the **pack manifest** (system prompt listing available packs and their descriptions)
2. Decide which pack(s) to query
3. Formulate search queries
4. Read retrieved chunks
5. Synthesize a grounded answer with `<cite chunk="cN"/>` markers
6. Refuse gracefully if no available pack covers the question

The model must **generalize to new packs at inference time** without retraining — achieved by training on many synthetic pack manifests.

## Architecture (locked in)

### Protocol

```
[SYSTEM]
<packs>
poetry: Telugu classical and modern poetry
te-wiki: Telugu Wikipedia
web: Live internet search
</packs>

[USER]
అన్నమయ్య సాహిత్యం గురించి చెప్పండి
(Tell me about Annamayya's literature)

[MODEL emits]
<search source="poetry">అన్నమయ్య సాహిత్యం</search>

[HARNESS injects]
<retrieved>
  <doc id="c1">[real chunk from poetry backend]</doc>
  <doc id="c2">[another chunk]</doc>
</retrieved>

[MODEL emits, possibly with more searches]
<search source="te-wiki">అన్నమయ్య కవి జీవితం</search>

[HARNESS injects]
<retrieved>
  <doc id="c3">[Annamayya Wikipedia entry]</doc>
</retrieved>

[MODEL emits final answer]
అన్నమయ్య (1408–1503) తెలుగు సాహిత్యంలో ముఖ్యమైన కవి <cite chunk="c3"/>.
ఆయన భక్తి కావ్యాలను రచించారు <cite chunk="c1"/>...
```

### What the model does vs the harness

| Block | Generated by | Loss |
|---|---|---|
| `<packs>...</packs>` system prompt | Harness/app | MASKED |
| User question | User | MASKED |
| `<search source="X">query</search>` | **MODEL** | TRAINED |
| `<retrieved>...</retrieved>` block | Harness (runs FAISS) | MASKED |
| `<no-search/>` | **MODEL** | TRAINED |
| Final answer text + `<cite chunk="cN"/>` markers | **MODEL** | TRAINED |

The model never produces retrieval content. Retrieval is always done by the harness using a deterministic FAISS+e5 pipeline.

### Key design decisions

| Decision | Choice | Rationale |
|---|---|---|
| Pack manifest format | System prompt with name + description per pack | Explicit, model can route by description |
| Citation format | Generic `<cite chunk="cN"/>` only | Metadata stays in the chunk record on disk; UI layer handles display |
| `<think>` blocks | Dropped for v1 | 225M is too small to benefit from CoT scratchpad |
| Multi-pack query style | Sequential only | Simpler for 225M; 2-3 hop max realistic |
| Citation IDs | Session-local (`c1`, `c2`, ...) | Assigned by harness at injection; app maintains mapping to stable per-pack chunk IDs |
| Embedding model on device | e5-small-multilingual @ int8 (~30 MB) | Single shared encoder for all packs |
| Inference-time pack additions | No retraining needed | Achieved via 200+ synthetic name diversity in training |

## Retrieval architecture

Two distinct steps, with the model only involved in the language tasks:

```
Step 1 — ROUTING + QUERY FORMULATION (model's job)
  Model reads pack manifest + question.
  Model emits: <search source="poetry">[query]</search>

Step 2 — RETRIEVAL (harness's job; model NOT involved)
  Harness maps source name → real backend.
  e5-small encodes query.
  FAISS nearest-neighbor over precomputed chunk embeddings.
  Returns top-K chunks.
  Harness wraps as <retrieved><doc id="c1">...</doc>...</retrieved>.

Step 3 — SYNTHESIS (model's job)
  Model reads retrieved chunks.
  Writes grounded answer with <cite chunk="cN"/> markers.
```

The model is purely a language router + synthesizer. Retrieval is pure math.

## Real backends (5-6 needed)

These are the actual FAISS indexes that exist at training and inference time. **You do NOT need 200 real packs** — just these:

| Backend ID | Source | Effort | Notes |
|---|---|---|---|
| `te-wiki` | Telugu Wikipedia + AI4Bharat content | 0.5 day | Re-embed existing data with e5-small-multilingual |
| `en-wiki` | English Wikipedia subset | 0.5 day | Use a 1-2M article subset for size |
| `poetry` | Telugu poetry corpus | 1-2 days | Sources: AndhraBharati, Project Madurai, Sangraha literary subset. ~50K verses target |
| `textbook` | NCERT + AP-Board textbooks | 3-5 days | PDF parsing, 4-6 subjects, chunked by section. LONGEST POLE — defer to v2 if needed |
| `web` | Brave or Tavily API | 0.5 day | Wrapper + response cache for reproducibility |
| `books` *(optional)* | Public-domain Telugu literature | 2-3 days | Stage B v2+ |

Each backend ships as: `manifest.json + chunks.bin + chunks.offsets + embeddings.fp16.bin + metadata.bin`.

## Synthetic name layer (the 200+ "packs")

Per training trace, the orchestrator generates a **random pack manifest** that renames the real backends. This is what makes the model generalize to new packs.

```python
poetry_pool = [
  ("kavithalu", "Modern Telugu poetry collection"),
  ("sanskruta-grantha", "Sanskrit texts with Telugu translations"),
  ("vacana-sahityam", "Telugu prose-poetry tradition"),
  ("padyalu-padalu", "Classical Telugu verse with prosody notes"),
  ("bhakti-sahityam", "Devotional Telugu literature"),
  # ... ~50 entries total
]
textbook_pool = [
  ("ncert-history", "NCERT History textbooks Classes 8-12"),
  ("ap-board-physics", "Andhra Board Physics Class 11-12"),
  ("class10-science", "Class 10 Science notes"),
  ("curriculum-2023", "Telangana state curriculum books"),
  # ... ~50 entries total
]
wiki_pool = [
  ("te-wiki", "Telugu Wikipedia"),
  ("encyclopedia", "Comprehensive general knowledge"),
  ("knowledge-base", "Facts and entity information"),
  # ... ~50 entries total
]
web_pool = [
  ("live-search", "Live internet search"),
  ("current-affairs", "Real-time news and updates"),
  # ... ~50 entries total
]
```

**Total: ~200 synthetic names across 4-5 pools.** Each trace samples 3-5 of them (mixing pools).

### Constraint: description-content alignment

A synthetic name's description must be plausibly consistent with the real backend it maps to. The orchestrator only assigns names from the appropriate pool. E.g., a synthetic name mapped to the `poetry` backend can never be called "Mathematical Foundations" — it must describe something the poetry backend actually contains.

## Trace generation

### Teacher

**Gemini 2.5 Flash** for bulk (cheaper, fast, decent Telugu).
**Gemini 2.5 Pro** for ~10K quality stratum (better Telugu nuance).

### Per-trace algorithm

```
1. Sample manifest: 3-5 synthetic packs from pools, mixed backends
2. Sample question type (weighted):
     - 30% single-pack routing
     - 15% multi-pack synthesis
     - 15% wrong-pack recovery
     - 10% no-search-needed
     - 10% multi-hop within one pack
     - 10% refusal (none of the packs help)
     -  5% adversarial (false premise, anachronism)
     -  5% mixed-language (Telugu Q with English content packs, etc.)
3. Generate seed question (Gemini, given manifest)
4. Loop with Gemini as the model:
     a. Gemini emits <search source="X"> or final answer
     b. If search: orchestrator maps synthetic name → real backend,
        runs FAISS, returns chunks with session-local IDs (c1, c2, ...)
     c. Loop until Gemini emits final answer (max 4 search rounds)
5. Quality checks:
     - Every <cite chunk="cN"/> references a chunk that was actually retrieved
     - Cited chunk content actually supports the claim (Gemini-as-judge)
     - No mid-trace formatting errors
     - Length within reasonable bounds (200-3000 tokens)
6. Save trace as JSONL: {manifest, conversation_turns, metadata}
```

### Dataset target

100K traces for v1. 150K if we want headroom.

### Cost estimate (Gemini 2.5 Flash, prices as of plan date)

Per trace:
- Input: ~2500 tokens (manifest 200 + question 30 + retrieved 2000 + few-shot prompt)
- Output: ~600 tokens (queries + answer + citations)

For 100K traces:
- Input: 250M tokens × $0.15/M ≈ **$38**
- Output: 60M tokens × $0.60/M ≈ **$36**
- 10K Pro stratum: ~$50 extra
- **Total: ~$125** (well under $200)

## SFT training

### Data format

JSONL, one trace per line:
```json
{
  "manifest": "<packs>kavithalu: ...\nncert-history: ...</packs>",
  "user": "...",
  "turns": [
    {"role": "model", "text": "<search source=\"kavithalu\">...</search>"},
    {"role": "harness", "text": "<retrieved>...</retrieved>"},
    {"role": "model", "text": "<final answer with <cite chunk=\"c1\"/>>"}
  ]
}
```

### Loss masking

- `manifest`: MASKED
- `user`: MASKED
- `turns[role==model]`: TRAINED
- `turns[role==harness]`: MASKED

The trainer flattens turns into a single sequence with EOS separators, and builds a boolean loss mask over the resulting tokens.

### Hyperparameters

- Starting checkpoint: `checkpoints/stage-a/final.pt` (val=3.05)
- LR: 1e-5 (low, preserve Stage A capabilities)
- Effective batch: 64-128 sequences
- Epochs: 2-3 over the trace set
- Warmup: 500 steps
- Schedule: WSD or cosine
- Block size: 4096 (existing model setting)
- Wall time on B200: ~4-6 hours

### Evaluation

Hand-curated **1-2K trace eval set** covering:
- Each pack type
- Multi-pack scenarios
- Refusal cases
- Adversarial cases (false premises, anachronisms)
- Out-of-manifest questions (model should route to `web` or refuse)
- Brand-new pack names not in training (test the generalization claim)

Metrics:
- **Routing accuracy**: did the model pick the right pack?
- **Query quality**: did the search query retrieve useful chunks? (auto-evaluated by checking retrieved chunks against gold)
- **Groundedness**: every factual claim cited? (Gemini-as-judge)
- **Citation precision**: each cited chunk actually supports the claim? (Gemini-as-judge)
- **Refusal calibration**: when retrieval is poor, does model abstain?
- **Generalization**: works on synthetic names not seen during training? (sanity check)

## Mobile deployment shape (informs pack-build format)

### Offline pack file format

```
<pack-name>.pack/
├── manifest.json         # name, version, description, embedding_model_id, chunk_count
├── chunks.bin            # gzipped sequential chunk texts
├── chunks.offsets.bin    # int32 array of byte offsets
├── embeddings.fp16.bin   # (N_chunks, 384) fp16 array — e5-small dim
├── metadata.bin          # per-chunk fields (poet, page, etc.) packed
```

### Size envelope per pack

| Pack size | Chunks | Total on-device size |
|---|---|---|
| Small (focused topic) | 1K | ~3 MB |
| Medium (one textbook series) | 10K | ~30 MB |
| Large (Telugu Wikipedia) | 200K | ~550 MB |

With int8 quantization on embeddings, halve those.

### Device-side encoder

**e5-small-multilingual @ int8** (~30 MB), shipped with the app once, used to encode all queries for all packs. Pack-side embeddings must be computed with this SAME model at pack-build time for compatibility.

### Online packs

Wikipedia-online and web ship ZERO content to the device — just name + description + endpoint URL. App calls the backend API at query time.

Synthetic-name → real-backend mapping table.
Chunk record with metadata stored separately from cite token.
Pack manifest format spec.

### Phase 2 — Real backends (3-7 days, parallel)
Priority order (start v1 with first three):

2. `poetry` — source corpus, chunk, embed, FAISS
3. `web` — Brave/Tavily wrapper + cache layer
4. `textbook` — defer to v2 (LONGEST POLE)
5. `en-wiki` — same as te-wiki
6. `books` — v2+

### Phase 3 — Synthetic name pools (0.5 day)
Generate 50 names + descriptions per pool. Gemini-generated, human-reviewed.

### Phase 4 — Trace generation pipeline (2-3 days build)
Orchestrator: question generation, manifest sampling, Gemini loop, FAISS retrieval, quality filtering, JSONL output.

### Phase 5 — Trace generation run (1-2 days)
Generate 100K traces. Cost ~$125. Bottleneck: Gemini API rate limits.

### Phase 6 — Dataset prep (1 day)
Filter, dedup, tokenize, pack into binary shards. Build loss masks.

### Phase 7 — SFT training (4-6 hours on B200)
Standard training loop with masked CE loss.

### Phase 8 — Eval (1-2 days)
Build eval set, run metrics, iterate on data if necessary.

### Total timeline
- **Stage B v1** (te-wiki + poetry + web, no textbook): **~7-10 days**
- **Stage B v2** (+ textbook): **~14-18 days** total

## Risks & open questions

1. **Poetry corpus quality**: Telugu poetry sources vary in cleanliness. May need careful normalization (Unicode, anumlt, vowel signs). Estimated 1-2 days of cleanup beyond initial sourcing.

2. **Textbook PDF parsing**: NCERT PDFs are clean enough; AP-Board may not be. If textbook is delayed, ship v1 without it.

3. **Gemini Telugu nuance**: 2.5 Flash may produce stilted Telugu in some genres (poetry, formal writing). Sample 1K traces early and human-spot-check before scaling to 100K. If quality is poor, switch to Gemini 2.5 Pro for the genres where it matters (poetry, refusals).

4. **Refusal-case fluency**: graceful refusals in Telugu need to be natural. Hand-curate ~100 refusal exemplars to seed Gemini's behavior.

5. **Multi-pack reasoning at 225M**: sequential multi-hop is in scope, but the model may struggle with >2 hops. Plan: target 1-2 hop reliably; treat 3-hop as best-effort.

6. **Eval-set staleness**: synthetic eval questions may differ from real user queries. Plan a small human-curated eval set (200 questions) representing realistic user intents.

7. **No retraining = no new citation field types**: we picked generic `<cite chunk="cN"/>` to enable zero-retrain pack additions. If a future pack needs a fundamentally different citation style (e.g., timestamped video chunks), that may require Stage B retraining with examples.

## Locked-in conventions (do not change without retraining)

- **Special tokens** (already in tokenizer-new-v5, vocab IDs 47822-47830):
  - `<search>` / `</search>`
  - `<retrieved>` / `</retrieved>`
  - `<doc>` / `</doc>`
  - `<cite>` (used as `<cite chunk="cN"/>` with attribute)
  - `<think>` / `</think>` — reserved but unused for v1
- **Citation attribute name**: `chunk` (always)
- **Source attribute name**: `source` (always)
- **Chunk ID format**: `c1`, `c2`, ... — session-local
- **No-search marker**: `<no-search/>`
- **Pack manifest format**: `<packs>\n<name>: <description>\n...</packs>`

Any deviation from these requires Stage B retraining.
